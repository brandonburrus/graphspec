# graphspec

**graphspec** is a CLI + library for *spec-driven development*: author software specs as a
**knowledge graph**, then build software by traversing it.

A spec is an [Open Knowledge Format (OKF) v0.1](https://okf.md/spec) bundle — a directory of
markdown files with YAML frontmatter, cross-linked by typed relations — constrained by the
**graphspec profile**. Because the spec is a graph rather than a document, an agent can pull
just the subgraph for the unit of work in front of it instead of re-reading a 40-page design
doc, and `coverage` can tell you mechanically which requirements nothing implements or tests.

graphspec knows OKF and the graphspec profile. Nothing else.

## Quickstart

### With a coding agent

Install the two agent skills with the [skills](https://skills.sh) CLI:

```bash
npx skills add brandonburrus/graphspec
```

Works with Claude Code, Cursor, Codex, Copilot, Windsurf, Gemini, and others. Then just ask:

> "Spec out the checkout flow as a graphspec."
> "Implement the next component from the spec."

`create-graph-spec` handles authoring; `follow-graph-spec` handles implementing from an
existing bundle, pulling one subgraph at a time and turning each `TestScenario` into a real
test. See [Agent skills](#agent-skills).

### Directly

No install needed:

```bash
npx graphspec validate spec/
npx graphspec coverage spec/
npx graphspec graph spec/ --format mermaid
```

Requires Node.js >= 20.

## How a spec is stored

- **Bundle** — a directory of `.md` files forming one spec.
- **Concept** — a file named `<name>.<type-token>.md`: YAML frontmatter + markdown body. Its
  **ID** is the bundle-relative path minus `.md`.
- **Reserved files** — `index.md` (directory listing) and `log.md` (change history) at any
  level. Generated by `index`; not concepts.
- **Ignored files** — any other `.md` with no `.<type-token>` segment, like `AGENTS.md` or
  `README.md`. Skipped rather than treated as malformed, so ordinary docs live happily inside
  a bundle. `validate` lists what it skipped, so a concept that lost its token surfaces
  instead of silently disappearing.
- **Relations** — typed edges declared in frontmatter. A target is a bundle-relative path
  with a leading `/`, with or without `.md`:

```yaml
---
type: Feature
title: Checkout
relations:
  includes:
    - /specification/payment.requirement.md
    - /specification/tax.requirement.md
---
```

## The profile

The vocabulary is **closed**: 13 node types, 16 relations. The filename token is the
kebab-case form of the type (`login.requirement.md`, `auth.system.md`,
`checkout.user-journey.md`).

| Layer | Type | Token | Required frontmatter | Conventional sections |
|-------|------|-------|----------------------|-----------------------|
| Product | UserPersona | `user-persona` | — | Goals, Pains |
| Product | UserJourney | `user-journey` | — | Flow |
| Product | Feature | `feature` | — | Summary |
| Architecture | System | `system` | — | Responsibility |
| Architecture | Component | `component` | — | Responsibility |
| Architecture | Integration | `integration` | `direction` (inbound\|outbound\|bidirectional) | Interface |
| Architecture | Contract | `contract` | — | Interface |
| Architecture | DataModel | `data-model` | — | Schema |
| Specification | Requirement | `requirement` | `status` (proposed\|accepted\|implemented\|verified) | Acceptance Criteria |
| Specification | Constraint | `constraint` | `category` (free string) | Rationale |
| Specification | Decision | `decision` | `status` (proposed\|accepted\|superseded) | Context, Decision, Consequences |
| Specification | TestScenario | `test-scenario` | `level` (unit\|integration\|e2e) | Given/When/Then |
| Glossary | Term | `term` | — | — |

| Relation | Source → Target |
|----------|-----------------|
| experiences | UserPersona → UserJourney |
| exercises | UserJourney → Feature |
| includes | Feature → Requirement |
| realizes | Component, System → Feature |
| contains | System → Component |
| depends-on | Component → Component, System → System |
| exposes | Component, System → Contract |
| uses | Component → DataModel, Contract |
| connects | Integration → System, Contract |
| satisfies | Component, System → Requirement |
| refines | Requirement → Requirement |
| constrains | Constraint → System, Component, Requirement |
| covers | TestScenario → Requirement, Component, UserJourney |
| supersedes | Decision → Decision |
| affects | Decision → (any type) |
| refers-to | (any type) → Term |

There is no fixed directory layout. Group concepts however you like.

## Validation

Two layers, deliberately separated:

- **OKF conformance — hard errors.** Every concept file needs a parseable YAML frontmatter
  block with a non-empty `type`. That is the whole list. Unknown types, broken cross-links,
  and missing optional fields never hard-fail; OKF is intentionally permissive.
- **Profile checks — warnings, promoted to errors by `--strict`.** Filename token agrees with
  `type`; required fields present and in-enum; relation names in the vocabulary; source type
  may originate the relation; each resolved target has an allowed type.

One deliberate exception: **unresolved relation targets stay warnings even under `--strict`**,
because OKF supports reference-first authoring — linking a concept before you write it.

## Commands

| Command | What it does | Flags |
|---------|--------------|-------|
| `validate [path]` | OKF conformance + profile checks | `--strict` `--json` |
| `query [path]` | Filter concepts, print a table | `--type` `--tag` `--status` `--json` |
| `index [path]` | Regenerate `index.md` listings, append to `log.md` | `--log <msg>` `--no-index` `--dry-run` |
| `graph [path]` | Emit the graph as JSON, Mermaid, or DOT | `--format` `--from` `--depth` `--rel` `--direction` `--structure` |
| `coverage [path]` | Report spec-graph gaps | `--json` `--strict` |
| `order [path]` | Topological build order over `depends-on` | `--json` |

`path` defaults to `.`. Exit codes: **0** success, **1** the spec failed the check (validation
errors, coverage gaps under `--strict`, a dependency cycle), **2** you invoked it wrong (bad
flag, unreadable bundle).

```bash
# Pull just the subgraph for one unit of work.
npx graphspec graph spec/ --from architecture/validator.component --depth 1
npx graphspec graph spec/ --from /architecture/validator.component.md   # same thing
npx graphspec graph spec/ --from specification/strict-mode.requirement --direction in

# What is unimplemented or untested? Non-zero under --strict, so CI can gate on it.
npx graphspec coverage spec/ --strict

# What should be built first?
npx graphspec order spec/

# Regenerate listings after adding concepts.
npx graphspec index spec/ --log "Added the payments feature."
```

`--from` takes a concept ID or the same `/path.md` reference form used in `relations:`.
`--direction in` walks edges backward, which is how you find what `covers` or `constrains` a
concept, since those relations originate elsewhere.

## Library API

```ts
import { loadBundle, Graph, validateBundle, PROFILE } from "graphspec";
import { selectSubgraph, buildOrder, analyzeCoverage } from "graphspec";

const bundle = await loadBundle("spec");
const graph = Graph.fromBundle(bundle);

validateBundle(bundle, { strict: true });                                  // diagnostics
selectSubgraph(graph, { from: "architecture/validator.component", depth: 1 });
buildOrder(graph);                                                          // { order, cycles }
analyzeCoverage(graph);                                                     // gap report
```

`npm install graphspec`. ESM-only: import it, don't `require` it. `PROFILE` is the single
source of truth for the vocabulary if you're building on top.

## Agent skills

[`skills/`](skills/) holds two portable Agent Skills (the `SKILL.md` directory convention,
with no dependency on any particular agent runtime):

- **[`create-graph-spec`](skills/create-graph-spec/SKILL.md)** — turn an intent (a feature
  idea, a system design, a decision to record) into a valid bundle: filename and frontmatter
  conventions, wiring `relations:`, and iterating `validate` → `--strict` → `index` → `query`
  until it's clean.
- **[`follow-graph-spec`](skills/follow-graph-spec/SKILL.md)** — implement from an existing
  bundle by pulling only the relevant subgraph per unit of work, in `order`-derived sequence,
  porting each covering `TestScenario` into a real test.

```bash
npx skills add brandonburrus/graphspec              # both, interactive
npx skills add brandonburrus/graphspec --all        # both, no prompts
npx skills add brandonburrus/graphspec -s create-graph-spec
```

Or copy the directories into wherever your agent runtime keeps skills.

## Example bundle

[`spec/`](spec/) is graphspec specified in graphspec — the dogfood bundle and the worked
example. It stays clean:

```bash
npx graphspec validate spec/ --strict   # 27 concept(s), 0 error(s), 0 warning(s)
npx graphspec coverage spec/            # 0 gap(s)
```
